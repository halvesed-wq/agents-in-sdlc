`quality-checks` 스킬로 자동 검사를 실행하고 Playwright MCP로 브라우저에서 필터링 경험을 확인했습니다. 이제 명확한 QA 절차를 정의하는 사용자 지정 에이전트로 두 기능을 함께 사용합니다.

이 레슨에서는 다음을 수행합니다.

- 사용자 지정 에이전트가 지침, 스킬, MCP 도구를 함께 사용하는 방식을 살펴봅니다.
- 재사용 가능한 품질 보증 프로필을 만들고 검토합니다.
- QA 에이전트를 선택하고 필터링 이슈에 따라 결과를 검토합니다.

## 시나리오

Tailspin Toys는 풀 리퀘스트(PR)를 열기 전에 요구 사항, 코드 품질, 자동 검사, 테스트 범위, 브라우저 동작을 일관되게 검토하려고 합니다. 사용자 지정 에이전트를 사용하면 QA 절차를 조율하고 재사용 가능한 보고서를 만들 수 있습니다.

## 사용자 지정 에이전트란?

사용자 지정 에이전트는 Markdown 프로필로 정의하는 특화된 Copilot입니다. 프로필에는 에이전트의 목적, 지침, 사용할 수 있는 도구가 포함됩니다. 이 워크숍에서는 `.github/agents/qa.agent.md`에 QA 역할을 정의하고 Copilot CLI에서 선택합니다.

지금까지 사용한 사용자 지정 기능은 각각 다른 역할을 합니다. 리포지토리 지침은 팀 표준을 설명합니다. `quality-checks` 스킬은 반복 가능한 검사를 제공합니다. Playwright MCP는 브라우저 도구를 제공합니다. QA 프로필은 Copilot에 해당 기능을 사용해 요구 사항을 평가하고 결과를 보고하는 방법을 알려 줍니다. 다른 기능을 대체하거나 별도의 대화를 요구하지 않습니다.

## QA 프로필 만들기

기능 PR을 열기 전에 Copilot에 재사용 가능한 QA 프로필을 만들어 달라고 요청합니다. 프로필에는 QA가 수행할 검사와 반드시 지켜야 할 경계가 모두 포함됩니다.

1. Codespace로 돌아가 필터링 대화가 Interactive 모드인지 확인합니다.
2. 기본 에이전트에 새 사용자 지정 에이전트를 만들도록 요청합니다.

   ```plaintext
   .github/agents/qa.agent.md에 QA라는 사용자 지정 에이전트를 만들어 주세요. 이 에이전트는 이슈와 합의된 요구 사항에 따라 기능을 확인하고, 리포지토리 지침을 따르고, quality-checks 스킬을 실행하고, Playwright MCP로 동작을 검증하고, 테스트 범위가 부족하면 테스트를 추가해야 합니다.

   각 요구 사항을 근거와 함께 통과, 실패, 차단으로 보고해야 합니다. 구현 코드를 변경하기 전에 먼저 물어봐야 하며, 변경 사항을 커밋하거나 풀 리퀘스트를 열어서는 안 됩니다.

   지금은 검토할 프로필만 만들어 주세요.
   ```

## 프로필 검토하기

새 에이전트를 사용하기 전에 프로필을 검토하여 의도한 QA 작업 흐름과 경계가 반영되었는지 확인합니다. 확인만 요청했는데 에이전트가 기능을 변경하거나 범위가 지나치게 넓어지는 일을 방지합니다.

1. `/diff`를 입력하고 `.github/agents/qa.agent.md`를 엽니다.
2. frontmatter를 읽습니다. `description`은 필수이며 `name`은 선택 사항입니다. `name`을 지정하면 에이전트를 명확하게 표시할 수 있습니다.
3. 프로필 지침을 읽고 QA가 요구 사항에서 시작하고 리포지토리 지침을 따르고 `quality-checks` 스킬을 실행하고 Playwright MCP를 사용하는지 확인합니다.
4. QA가 근거를 보고하고 구현 코드를 변경하기 전에 확인을 요청하며 변경 사항을 커밋하거나 PR을 만들지 않는지 확인합니다.
5. 프로필에서 이러한 책임이나 경계가 빠져 있다면 계속하기 전에 기본 에이전트에 수정을 요청합니다.

## 이슈를 기준으로 QA 실행하기

Copilot CLI는 대화가 시작될 때 프로젝트 에이전트를 불러옵니다. 프로필을 만든 뒤 동일한 필터링 대화를 다시 시작하고 QA를 선택하여 기존 이슈와 계획의 결정 사항을 사용하게 합니다.

1. 다음 프롬프트를 입력해 에이전트를 활성화합니다.

   ```plaintext
   /agent QA
   ```

> [!NOTE]
> 방금 에이전트를 만들었기 때문에 사용 가능한 에이전트 목록에 표시되지 않을 수 있습니다. 에이전트는 존재하며 위 명령으로 활성화할 수 있습니다.

2. 다음 프롬프트로 QA 에이전트에 기능을 검토하도록 요청합니다.

   ```plaintext
   이슈와 계획에서 결정한 내용에 따라 필터링 기능을 검토해 주세요. PR을 열 준비가 되었나요?
   ```

3. QA 에이전트가 작업하는 과정을 살펴봅니다.
4. 작업이 끝나면 결과 보고서를 읽습니다.

## 요약 및 다음 단계

재사용 가능한 전문 역할을 작업 흐름에 추가하고 그 결과를 검토했습니다. 이 레슨에서는 다음을 수행했습니다.

- 사용자 지정 에이전트가 지침, 스킬, MCP 도구를 함께 사용하는 방식을 살펴봤습니다.
- 재사용 가능한 QA 프로필을 만들고 검토했습니다.
- QA 에이전트를 선택하고 필터링 이슈에 따라 결과를 검토했습니다.

이제 구현, 스킬 업데이트, QA 프로필, 테스트, 검증 보고서를 검토할 준비가 되었습니다. 다음으로 [기능 PR을 만들고 Agent Merge를 사용합니다][next-lesson].
